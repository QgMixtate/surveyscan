# SurveyScan

Платформа постоянной инвентаризации и реестра ИТ-активов. В репозитории две версии:

| Версия | Где | Статус |
|---|---|---|
| **v2 (Go) — основная разработка** | [`v2/`](v2/) | Активная разработка; план из 50 пакетов, принято 57/200 подзадач |
| v1 (Python) — legacy-сканер | корень (`surveyscan/`, `collectors/`, `connector/`, …) | Сохраняется и поддерживается; новые функции не добавляются |

## v2 — постоянный реестр ИТ-активов (Go)

Постоянный реестр вместо разовых сканов: данные поступают непрерывно и сводятся в карточку актива с историей и происхождением.

- **Источники данных:** постоянный агент на Linux (systemd) и Windows (служба SCM); площадочный collector; безагентный сбор по SSH, WinRM и SNMPv3; разовый portable-аудит без установки службы (файл или HTTPS-загрузка).
- **Центр:** приём подписанных наблюдений (mTLS, Ed25519), сопоставление с активами (в т.ч. автоматическое сведение по сильным идентификаторам), проекции фактов, история, outbox и аудит; секреты и ключи — в OpenBao.
- **Интерфейсы:** отдельный Web UI (реестр, карточка актива с инвентаризацией из 12 разделов, источники, **схема сети L3**), CLI `surveyscanctl`, HTTP API с JSON-Schema-контрактами.
- **Стек:** Go 1.27, PostgreSQL 17, OpenBao 2.7, React 19 + TypeScript (без CDN, закрытый контур), nginx; dev-стенд на Docker Compose.

## Legacy v1 (Python): сканер инвентаризации с автопостроением схемы сети

**Назначение (текущий фокус):** сетевое обнаружение активов, **аутентифицированный сбор инвентаря по УЗ** и **автоматическое построение схемы сети**. Указываете подсети/хосты (и, по желанию, учётные записи) → surveyscan выполняет сетевой скан (nmap), затем подключается к активам по SSH/WinRM/SNMP и собирает полный инвентарь, раскладывает активы по подсетям и строит **интерактивную схему сети** (ядро → устройства → подсети → хосты) с экспортом в **PNG/SVG**.

```
Цели (10.0.0.0/24, host…) + набор УЗ → nmap (-sV -O) → активы+сервисы
                                      → SSH/WinRM/SNMP: полный инвентарь (подбор УЗ под актив)
                                      → схема L3 (+L2 по SNMP) → граф в вебе + PNG/SVG
```

- **Сетевое обнаружение (nmap):** живые хосты, открытые сервисы (порт/протокол/версия), ОС/платформа.
- **Аутентифицированный сбор по УЗ:** учётные записи заводятся один раз в хранилище (вкладка «Учётные записи», секреты шифруются в БД, ключ — в `SURVEYSCAN_SECRET_KEY`), в скане выбираются галочками. К каждому активу подбирается подходящая УЗ и запускается «родной» коллектор — `linux_collect.sh` по **SSH** (пакеты, учётки, параметры ОС, конфиги) и `windows_collect.ps1` по **WinRM** (ПО, роли, патчи). При скане секрет расшифровывается только в память задачи; в БД задачи, логи и отчёт не попадает.
- **Схема сети L3:** группировка по /24, выделение шлюзов/устройств, сведение к ядру.
- **Схема L2 (по SNMP):** опрос оборудования (sysName/sysDescr, LLDP-соседи) достраивает связи L2 на схеме.
- **Визуализация:** интерактивный граф (cytoscape, клик по узлу → карточка актива, раскладки «Слои»/«Свободно») + серверный экспорт **SVG** и клиентский **PNG**.
- **Контроль задачи:** карточка скана с живым журналом выполнения (фазы nmap/сбора, прямо в UI), разбивкой сбора по активам (что собралось / что не удалось и почему), кнопками **Отменить** (убивает процесс nmap) и **Повторить**.

> Это инструмент обследования, а не сертифицированное средство анализа защищённости.

<details><summary>Наследие: модули уязвимостей (БДУ ФСТЭК) и проверки конфигураций</summary>

Пайплайн по-прежнему умеет сопоставление с БДУ ФСТЭК/MSRC/фидами и проверки конфигураций по профилям (приказы 117 / 21 / 239, CIS), но в UI они скрыты — продукт сфокусирован на инвентаризации и схеме сети. Профили скана `vuln`/`config` остаются доступны через API.

### Быстрый старт

```bash
pip install -r requirements.txt          # Python 3.10+, psycopg[binary]
# нужен работающий PostgreSQL; по умолчанию host=127.0.0.1 port=5433 user=surveyscan
export SURVEYSCAN_PG_DSN="host=127.0.0.1 port=5433 user=surveyscan"   # при необходимости
python -m surveyscan demo                # полный прогон на синтетических данных -> demo-output/report.html
python -m pytest -q                      # автотесты
```

> Этап 1 дорожной карты выполнен: ядро и весь пайплайн работают на **PostgreSQL**
> (наборы данных — схемы одной БД: `public` обследование, `bdu`, `ms` MSRC, `adv` фиды;
> адаптер `surveyscan/pgcompat.py` транслирует диалект, запросы не переписывались).

> Этап 2 выполнен: **бэкенд FastAPI + очередь задач** (вертикальный срез
> «создать задачу → запустить скан → получить результат через API»).
>
> ```bash
> python -m surveyscan.api                 # uvicorn на :8000 (нужен PostgreSQL)
 # POST /credentials {"name":"Linux-аудит","type":"ssh","username":"audit","secret":"…"} -> УЗ в хранилище
> # GET  /credentials              -> список УЗ (без секретов)
 # POST /tasks {"kind":"inventory","targets":"10.0.0.0/24","cred_ids":[1,2],"run":"async"} -> скан+сбор
 #       (cred_ids — выбранные УЗ из хранилища; "kind":"demo" -> прогон без сети)
> # GET  /tasks                    -> список задач
> # GET  /tasks/{id}               -> статус + сводка + dashboard (активы, топология)
> # GET  /tasks/{id}/topology      -> схема сети (узлы/связи + статистика) для графа
> # GET  /tasks/{id}/topology.svg  -> схема сети в SVG (экспорт)
> # GET  /tasks/{id}/report        -> HTML-отчёт
> # GET  /docs                     -> Swagger UI, /openapi.json -> схема API
> ```
>
> Ядро переиспользуется как библиотека (`surveyscan/api/runner.py`). Очередь сейчас —
> пул потоков (`run:async`); интерфейс `submit(task_id)` рассчитан на замену на
> Celery+Redis без изменения тела задачи. Каждая задача выполняется в своей рабочей БД
> PostgreSQL. Аутентификация, RBAC и мультиарендность — следующие этапы.

> Этап 3 выполнен: **веб-интерфейс (React) по макету A+**. SPA (`surveyscan/api/static/`)
> отдаётся бэкендом на `/`, общается с REST API: сайдбар, запуск обследования, список
> со статусами, дашборд со сводкой (уязвимости, снятые бэкпорты, соответствие профилей)
> и встроенный HTML-отчёт. React/ReactDOM вендорятся локально (`static/vendor/`), JSX
> предкомпилирован в `static/app.js` (`app.jsx` — исходник) — **без CDN и сборщика в рантайме**,
> подходит для закрытого контура. Открыть: `python -m surveyscan.api` → http://localhost:8000/

> Этап 4 выполнен: **коннектор на Go** (`connector/`) — агент сбора у заказчика.
> Всегда дозванивается до центра сам (**pull-модель**, только исходящие соединения —
> у заказчика не открываются входящие правила), для изолированного контура —
> **офлайн-курьер** (файловый обмен задание/результат). Статический бинарник без
> зависимостей. Серверная часть протокола — `surveyscan/api/connector.py`:
>
> ```
> POST /connectors                     регистрация коннектора -> токен
> POST /connector/jobs                 задание коннектору (assigned)
> GET  /connector/jobs/next            коннектор забирает задание (Bearer-токен)
> POST /connector/jobs/{id}/result     выгрузка сырья -> центр анализирует своими базами
> GET  /connector/jobs/{id}/bundle     экспорт задания для офлайн-курьера
> ```
>
> Коннектор собирает сырьё коллекторами (`collectors/*`), анализ (БДУ, фиды, конфиги)
> идёт на центре. mTLS — боевая аутентификация (`-ca/-cert/-key`), токен — минимальный
> вариант. Сборка и режимы — в `connector/README.md`.

### Рабочий процесс

```bash
# 1. Базы знаний (раз в сутки или перед обследованием)
python -m surveyscan bdu-import vulxml.zip                       # https://bdu.fstec.ru/files/documents/vulxml.zip
python -m surveyscan msrc-sync --months 2026-Sep 2026-Oct        # бюллетени Microsoft (или --file *.json офлайн)

# 2. Сбор
python -m surveyscan collect-ssh 10.10.1.11 --user audit --sudo --ask-pass       # один Linux-хост
ansible-playbook -i inventory.ini ansible/collect.yml --ask-vault-pass           # массово Linux + Windows
nmap -sV -oX nmap.xml 10.10.1.0/24                                               # сетевые сервисы
#    + отчёт Greenbone (XML), Trivy (JSON), конфигурации сетевого оборудования (.cfg)
#    закрытый контур: collectors/linux_collect.sh и collectors/windows_collect.ps1 запускаются на месте

# 3. Загрузка, анализ, отчёт
python -m surveyscan --survey work/acme.sqlite ingest raw/* nmap.xml openvas.xml configs/*.cfg
python -m surveyscan --survey work/acme.sqlite analyze --profile profiles/base.yaml --profile profiles/acme.yaml
python -m surveyscan --survey work/acme.sqlite report --out acme.html --csv acme-csv/ --name "ГИС «Пример»" --customer "ООО «Пример»"
```

### Что где лежит

| Путь | Назначение |
| --- | --- |
| `collectors/linux_collect.sh` | Коллектор Linux (POSIX sh, только чтение): ОС, пакеты, sysctl, sshd, PAM, учётки, права, порты, службы, аудит, режимы Astra |
| `collectors/windows_collect.ps1` | Коллектор Windows (PowerShell 5.1+, только чтение): ОС и сборка, KB, ПО, secedit, auditpol, реестр, брандмауэр, порты, антивирус |
| `ansible/collect.yml` | Массовый безагентный сбор (SSH / WinRM) |
| `surveyscan/bdu.py` | Потоковый импорт выгрузки БДУ (≈90 тыс. записей за ~20–45 с, ~40 МБ памяти) |
| `surveyscan/versions.py` | Сравнение версий dpkg / rpm и разбор русскоязычных диапазонов БДУ |
| `surveyscan/matcher.py` | Сопоставление: CVE→БДУ (сканеры, MSRC) и прямой поиск по БДУ; сведение дублей |
| `surveyscan/msrc.py` | Бюллетени Microsoft (CVRF v3) и сравнение по номеру сборки Windows |
| `surveyscan/advisories.py` | Фиды вендоров (Ubuntu OVAL, Debian JSON, нормализованный JSONL): CVE → исправленная версия пакета; снятие бэкпорт-ложняков |
| `surveyscan/configcheck.py` | Движок проверок конфигураций (проверки + каталог требований + профиль) |
| `rules/products.yaml` | Словарь «как ПО называется в БДУ ↔ имена пакетов / программ / сервисов» |
| `checks/*.yaml` | 101 проверка: Linux — 49 (+4 для Astra SE), Windows — 30, Cisco IOS — 12, Huawei VRP — 6 |
| `catalog/requirements.yaml` | Документы и привязка проверок к их пунктам (**черновик**, согласуется с консалтингом) |
| `profiles/*.yaml` | Профили: базовый и пример профиля заказчика с наследованием и переопределением порогов |
| `samples/` | Синтетические данные для демо и тестов (номера BDU:2099-* и CVE-2099-* не существуют) |

### Как добавить

**Проверку** — запись в `checks/*.yaml`:

```yaml
- id: LNX-SSH-07
  title: "SSH: баннер предупреждения"
  platform: linux
  fact: [sshd, banner]          # путь к факту из коллектора
  op: ne                        # eq ne ge le gt lt range in not_in regex not_regex empty not_empty
  value: none                   #   contains not_contains subset_of mode_le
  default: none                 # значение, если параметр не задан (умолчание ПО)
  missing: na                   # если данных нет совсем: na | fail | pass
  requires: []                  # проверки-условия
  severity: low
  remediation: "Banner /etc/issue.net"
```

и строку привязки в `catalog/requirements.yaml`. **Синоним продукта** — запись в `rules/products.yaml`. **Профиль заказчика** — файл в `profiles/` с `extends: base`, `exclude` и `params`.

### Безопасность данных обследования

- Коллекторы только читают: не собирают хэши паролей (`/etc/shadow` — только имена учёток с пустым паролем), не меняют настроек.
- Пароли, ключи и SNMP-сообщества в строках конфигурации маскируются в отчёте и CSV (`enable password ******`); стандартные `public`/`private` показываются — это и есть находка.
- В базе обследования (`*.sqlite`) хранятся сырые данные, включая полные конфигурации устройств: храните её как материалы заказчика (шифрованный носитель, удаление по договору).
- `collect-ssh` по умолчанию отклоняет неизвестный ключ хоста; пароль запрашивается интерактивно и не пишется на диск.

### Достоверность находок

| Значение | Когда |
| --- | --- |
| подтверждено (фид вендора) | Версия пакета старее исправленной по фиду вендора ОС; в отчёте — целевая версия и ссылка на бюллетень |
| подтверждено сканером | Находка OpenVAS / Trivy, обогащённая по CVE |
| высокая | ПО Windows / прошивка в диапазоне БДУ; ОС Windows по номеру сборки из бюллетеня MSRC |
| вероятно | Пакет дистрибутива Linux или версия сетевого сервиса в диапазоне БДУ, фид вендора не подключён — возможен бэкпорт |
| требует проверки | Диапазон версий БДУ не разобран (приложение А), либо записи нет в фиде вендора — сверить вручную |

**Бэкпорты исправлений.** Вендоры (Ubuntu/Debian/Astra/РЕД ОС) закрывают уязвимость, не меняя upstream-версию
(`openssh 8.4p1` остаётся `8.4p1`, фикс — в ревизии пакета). Поэтому для пакетов ОС вердикт строится по
**полной версии пакета** против версии из фида вендора (`advisories`), а не по upstream из БДУ: если установленная
версия ≥ исправленной — находка **снимается** (бэкпорт применён), иначе — «подтверждено (фид вендора)» с целевой
версией. Пока фид дистрибутива не подключён, такие находки остаются «вероятно»/«требует проверки», но не «уязвимо».

```bash
# Загрузка фидов (файлы скачиваются заранее — в закрытом контуре вручную)
python -m surveyscan adv-import \
  --ubuntu-oval com.ubuntu.jammy.pkg.oval.xml.bz2 \
  --debian-json debian-data.json \
  --file astra-1.7.jsonl          # нормализованный JSONL для Astra/РЕД ОС, пока нет их OVAL
```

### Проверено

- Автотесты: 74 (сравнение версий, разбор диапазонов, сквозной прогон, операторы, профили, маскирование секретов, фиды вендоров и снятие бэкпортов).
- Коллектор Linux и сбор по SSH (ключ, sudo с паролем, отказ на неизвестном ключе хоста) — на живой Ubuntu 24.04; Ansible-сбор Linux — там же.
- Коллектор Windows — синтаксис и разбор `auditpol` / `secedit` проверены в PowerShell 7.4; **на реальной Windows не запускался** — это первый шаг пилота.
- Импорт БДУ и анализ — на синтетической выгрузке объёма реальной (90 тыс. записей). На настоящей выгрузке не проверялся: сайт БДУ недоступен из среды разработки.
- Фиды вендоров — парсеры Ubuntu OVAL и Debian JSON проверены на синтетике тех же форматов; на astra-app01 OpenSSH корректно снимается как бэкпорт, sudo подтверждается с целевой версией. Живая загрузка фидов требует доступа к сайтам вендоров (в среде разработки закрыт egress-allowlist).

### Ограничения прототипа

- Хранилище — PostgreSQL (этап 1 выполнен: ядро и весь пайплайн на PostgreSQL, схема прежняя); нет веб-интерфейса и API.
- Сетевые устройства — проверки по тексту конфигурации; Batfish не подключён.
- СУБД — только как ПО/сервис для уязвимостей; SQL-проверки конфигурации СУБД не реализованы.
- Фиды вендоров: реализованы Ubuntu (OVAL) и Debian (JSON); Astra / РЕД ОС / Альт — через нормализованный JSONL, пока нет их машиночитаемых фидов (формат запрашивается у вендоров). Релиз Astra определяется по версии приближённо.
- Debian-фид keyed по исходному пакету, инвентарь — по бинарному: для Debian нужна карта бинарный→исходный пакет (для Ubuntu OVAL и нормализованного фида имена бинарные — совпадают).
- Отчёт DOCX по шаблону отдела не реализован (HTML + CSV).

# C35 — раздельные роли центра и несколько экземпляров

Статус: реализовано в песочнице (R-027, 2026-11-12). Доменная модель не менялась.

## Роли (C35.01)
`SURVEYSCAN_V2_ROLE` = `combined` (по умолчанию, как раньше) | `api` | `worker`.
| | combined | api | worker |
|---|---|---|---|
| UI/API, транспорт агентов и collector (mTLS) | да | да | нет (только `/health/live`, `/health/ready`) |
| Очередь событий (версии активов) | да | нет | да |
| Индекс поиска (применение событий, пересборка) | да | нет (только запросы к сервису поиска) | да |
| Уведомления (раздача и отправка) | да | нет (включение в Web — да) | да (подхватывает включение за ≤ 30 с) |
| Синхронизация с каталогом по расписанию | да | нет (ручной запуск из Web — да) | да |
| Продление токена OpenBao | да | да | да |
Длительная работа в HTTP: импорт portable-пакета и ручная синхронизация/пересборка остаются запросами
администратора с ограничением времени (как в C25/C29); по расписанию — только worker.

## Конкурентность без памяти процесса (C35.02)
| Работа | Защита от двойного выполнения |
|---|---|
| Потребитель версий активов | advisory-lock транзакции на (тенант, потребитель), отметка applied в той же транзакции |
| Индексатор поиска, раздача уведомлений | то же (ConsumeBatch) |
| Отправка уведомлений | `FOR UPDATE SKIP LOCKED` + аренда next_attempt_at (как минимум один раз; повтор отбрасывается по event_id) |
| Синхронизация каталога тенанта | сессионный advisory-lock `directory-sync:<тенант>` на выделенном соединении; занято — пропуск (ручной запуск — 409) |
| Пересборка индекса поиска | сессионный advisory-lock `search-rebuild`; занято — пропуск / 409 |
| Сессии, права, задачи | только PostgreSQL (любой api-экземпляр принимает сессию другого) |
Падение процесса снимает блокировку вместе с соединением.

## Поиск (C35.03, ADR C28)
Один сервис поиска (Tantivy) — единственный файловый индекс; писатель логически один: изменения вносят worker под
блокировкой потребителя, пересборку — один процесс под `search-rebuild`. api-экземпляры только читают через тот же
сервис и перепроверяют результаты по PostgreSQL. Несколько копий сервиса поиска (реплики индекса) — не
поддерживаются в этой версии: при недоступности сервиса поиск переходит в точный режим по PostgreSQL.

## Проверки (C35.04)
`scripts/split_smoke.py` (CI): api не потребляет очередь; два worker — только health, каждое событие применено ровно
один раз, версии сходятся; сессия api #1 действует на api #2, страницы одинаковы; после остановки api #1 api #2
читает и пишет, worker применяет новое событие. Интеграционные тесты: синхронизация каталога и пересборка поиска
при занятой блокировке другого процесса — 409/ErrBusy без побочных эффектов.
**Нагрузка в раздельном режиме** (песочница, паспорт C30: 2 000 активов, 100 пользователей, замер 300 с;
`research/load/results/r5-split.json`): api + 1 worker — 10 966 запросов, 36,6 запроса/с, ошибок 0, p95/p99 всех
94/199 мс; p95: список 29, «Мои задачи» 23, карточка 22, поиск 162, схема 71, правки 159, передача 158 мс; очередь
outbox и индекс в конце — 0. Все SLO D-18 выполнены (CPU и память api-процесса — 27 % ядра, 313 МиБ; worker не учитывался).
Не измерено: насыщение worker, разные хосты.

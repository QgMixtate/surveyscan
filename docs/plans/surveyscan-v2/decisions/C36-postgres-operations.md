# C36 — пул соединений, измерение запросов и обслуживание PostgreSQL

Статус: выполнено в песочнице (R-027, 2026-11-12); пулер на стенде не разворачивался (не нужен при одном процессе).

## C36.01 — пул соединений
**Сейчас (до ~4 процессов центра):** без отдельного пулера — у каждого процесса свой пул pgx
(`SURVEYSCAN_DB_MAX_CONNS`, по умолчанию 32). Сумма пулов всех процессов + запас для обслуживания должна быть меньше
`max_connections` PostgreSQL (по умолчанию 100): например, 2 api × 32 + 2 worker × 16 = 96 — уже на грани; при
раздельных ролях задавать worker `SURVEYSCAN_DB_MAX_CONNS=16` или поднять `max_connections`.
**Когда процессов больше или PostgreSQL общий:** PgBouncer ≥ 1.21 в режиме `transaction` с
`max_prepared_statements > 0` (pgx использует подготовленные запросы).
Совместимость кода с режимом transaction (проверено поиском по коду): нет `SET` сессии, временных таблиц,
`LISTEN/NOTIFY`, сессионных advisory-блокировок — взаимоисключение работ сделано арендой строки
`messaging.work_leases` (C35.02, миграция 0046), а блокировки потребителей — `pg_advisory_xact_lock` (в пределах
транзакции). Пулер не заменяет маршрутизацию шардов (C37) и отказоустойчивость PostgreSQL (C38).

## C36.03 — хранение и очистка (предложение; объёмы — по замеру C36.02)
| Данные | Политика | Почему так |
|---|---|---|
| События outbox и отметки потребителей | старше 30 дней и применены всеми **нужными** потребителями: версии активов — всегда; индекс поиска — если он настроен; раздача уведомлений — если у тенанта есть подписки | пересборка поиска идёт из PostgreSQL, а не из событий; уведомления рассылают только события после создания подписки |
| Доставки уведомлений | доставленные и dead — 30 дней | журнал для разбора, не источник истины |
| Журнал синхронизаций каталога | последние 500 прогонов тенанта | панель показывает 20 последних |
| Аренды работ | истёкшие — сразу | служебные |
| Наблюдения (подписанные данные сбора) | **не удаляются автоматически** | на них ссылаются текущие факты, история и пересборка карточек (C25); удаление — только отдельной процедурой по решению пользователя (срок хранения) |
| Аудит | **не удаляется автоматически** | срок — требование организации (решение пользователя) |
Очистка — фоновая работа worker раз в час, под арендой `retention`, пачками (без длинных транзакций), с итогом в журнале.

## C36.02 — профиль запросов (песочница, паспорт C30, pg_stat_statements; `research/load/results/r6-profile.json`)
4 353 запроса за 120 с, ошибок 0, p95/p99 92/182 мс; соединений PostgreSQL ≤ 12, активных ≤ 4 (пул не насыщен).
Самое затратное: (1) запись фактов 1.2 фоновым импортом — 18,6 мс × 800 (ожидаемо); (2) ожидание блокировки записи
тенанта `pg_advisory_xact_lock` — 7 мс × 1 759 (импорт, правки и потребители сериализуются на тенант — осознанный
выбор C06; узкое место при сильном росте одновременных записей одного тенанта); (3) построение схемы сети — 976 мс ×
5 (фоновый пересчёт кэша раз в 30 с, пользователь получает кэш; при росте — инкрементальный пересчёт);
(4) остальное — единицы миллисекунд. Оптимизации по фактам выполнены раньше (C30: пакетное чтение страниц).
Расширение включено только в dev/CI-стенде (`deploy/compose.yaml`); на стенде пользователя — по согласию.

## C36.04 — отказ PostgreSQL и пул (`scripts/pool_failover_smoke.py`, в CI)
Остановка БД под живым центром: API отвечает 503 сразу (без зависаний), запись в окне отказа не оставляет частичных
изменений; после возврата БД тот же процесс (без перезапуска) — пул переподключается, сессия действует, чтение и
запись работают, очередь событий догоняет. Архитектурный тест `TestNoSessionStateSQL` запрещает в коде сессионные
блокировки, `LISTEN`, временные таблицы, `SET`/`set_config(…, false)` — защита совместимости с пулером. Миграции
проверяются смоками upgrade/update (C13) на каждом коммите.

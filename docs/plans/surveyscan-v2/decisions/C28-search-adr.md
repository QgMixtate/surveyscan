# C28.03–C28.04 — результаты PoC поиска и выбор движка

Статус: предложено (R-027, 2026-11-11). Критерии и веса зафиксированы заранее — [C28-search-criteria](C28-search-criteria.md)
(коммит 1d7e371, до измерений). Код PoC и сырой отчёт — `v2/research/search-poc/` (`results-100k.json`).

## Как мерили (C28.03)
- Корпус: 100 000 активов (5 тенантов), затем 1 000 обновлений и 2 000 удалений; 30 запросов по фазам до/после изменений,
  ожидания посчитаны генератором. Каждый запрос — 50 повторов, один поток, тёплый кэш.
- Оба PoC делают одно и то же: построение, запросы, изменения одной фиксацией, запросы, пересборка с нуля.
  Разбор текста одинаковый: буквы/цифры как токены, нижний регистр, русские стоп-слова и стеммер Snowball;
  идентификаторы (хост, серийный номер, IP) — ключевые поля в нижнем регистре; FQDN — по частям с позициями.
- Машина: облачная песочница, 4 vCPU, 15 ГиБ. **Это не SLA**, а сравнение кандидатов в одинаковых условиях.

## Решение (C28.04)
**Tantivy** — движок полнотекстового поиска. PostgreSQL остаётся источником истины; индекс — пересобираемая проекция.

### Схема работы
- **Отдельный процесс `surveyscan-search`** (Rust, Tantivy) рядом с центром, не CGO: Go-монолит остаётся чистым
  Go со статической сборкой и простой кросс-сборкой; падение поиска не роняет центр.
- **Один писатель:** процесс поиска читает outbox центра (как обычный потребитель, со своей контрольной точкой)
  и применяет изменения документов; номер последнего применённого события хранится в payload фиксации Tantivy —
  после перезапуска применение продолжается с него.
- **Читатели:** API центра обращается к поиску по локальному сокету/loopback HTTP; поиск возвращает **кандидатов**
  (asset_uid + оценка), центр перепроверяет тенант и права по PostgreSQL перед ответом. Устаревший индекс не может
  раскрыть данные (ворота 3).
- **Снимки и восстановление:** индекс не бэкапится как данные — при потере, повреждении или смене формата между
  версиями Tantivy он пересобирается из PostgreSQL (порядок: 100 000 активов ≈ 1 с в PoC; на стенде измерить).
- **Без поиска** продукт работает: фильтры и поиск по идентификаторам остаются в PostgreSQL (C26, индекс имени ПО);
  полнотекстовый поиск — дополнительный сервис.

### Последствия
- В сборку и поставку добавляется Rust-тулчейн и второй бинарник (Linux; Windows — только если центр там понадобится).
- Нужен протокол «центр ↔ поиск» (запрос, ответ-кандидаты, здоровье, версия индекса) — контракт C29/C30.
- Вне Go-проверок архитектуры: поиск не пишет в PostgreSQL, только читает outbox.

### Оставшиеся риски
1. Опыт команды в Rust и сопровождение второго языка.
2. Формат индекса меняется между версиями Tantivy — допустимо при быстрой пересборке, но обновление центра должно
   уметь пересобирать индекс в фоне.
3. Морфология ФИО и сложные формы (прилагательные: «бухгалтерского» ≠ «бухгалтерия») — нужен лемматизатор или
   дополнительные поля; в PoC не решалось.
4. Измерения только на синтетике и одной машине; на стенде и реальных данных — повторить.
5. Bluge исключён из-за заморозки проекта (2022) и отставания по скорости; если требование «один бинарник без Rust»
   станет жёстким, вернуться к вопросу (альтернатива — Bleve v2, в C28 не измерялся).

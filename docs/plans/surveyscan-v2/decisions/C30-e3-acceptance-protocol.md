## 1. Нагрузка «100 активных пользователей» (C30.03, AC-43)
Паспорт — [C30-load-passport](C30-load-passport.md) (зафиксирован до прогонов, 358bef1). Инструмент — `v2/research/load`
(генератор на Go + обвязка с настоящим центром, сервисом поиска, фоновым импортом). Сводки — `v2/research/load/results/`.
Окружение: облачная песочница 4 vCPU / 15 ГиБ, PostgreSQL 16 в контейнере, центр в режиме combined, клиент на той же
машине (RTT ≈ 0). 2 000 активов с полной инвентаризацией 1.2 (≈ 700 пакетов ПО на актив), 100 учётных записей
(80 операторов, 15 наблюдателей, 5 администраторов), 100 субъектов, 50 сервисов; разогрев 60 с, замер 300 с,

### Узкие места и исправления (по данным, адресно)
1. **Начальный → повтор 1.** Схема сети на каждый запрос дважды сканировала все факты тенанта (p50 24 с) и держала
   соединения; пул из 8 соединений исчерпывался → 503 у всех. Исправлено: набор хостов из таблиц состояния разделов,
   кэш схемы на тенант 30 с с общим вычислением, пул 32 (настраивается `SURVEYSCAN_DB_MAX_CONNS`). (коммит 5746da9 «perf(C30.03): topology host set…»)
2. **Повтор 1 → 2.** Сервис поиска обрабатывал запросы в одном потоке под общей блокировкой и строил фрагменты для
   1 000 совпадений; индексатор фиксировал индекс на каждое событие и отставал от фонового импорта. Исправлено:
   многопоточный сервис, поиск по снимку читателя без блокировки, фрагменты только для показываемой страницы;
   пакетный индексатор (до 200 событий, актив — один раз); схема сети отдаёт прежний результат, пока считается новый.
3. **Повтор 2 → 3.** Страницы раздела 1.2 и вкладки ПО для каждой строки извлекали вид источника из многомегабайтного
   подписанного payload наблюдения. Исправлено: вид источника — из таблицы источников (совпадает с подписанным: центр
   сверяет его при приёме).
Каждое исправление проверено полным интеграционным набором до повторного замера.

### Оговорки
- Песочница, не стенд: железо, сеть (RTT ≈ 0) и данные (синтетический набор из одного реального хоста) отличаются
  от эксплуатации. Повтор на стенде — отдельный шаг.
- Гонки правок (ожидаемые 412) в замере не возникли: 100 пользователей на 2 000 активов редко правят один актив.
  Корректность конкурентных правок проверена интеграционными тестами (C25.04, C27.04), не нагрузкой.
- pg_stat_statements в песочнице не включено — медленные запросы найдены по профилю действий и разбору SQL.
- Масштабирование API/worker раздельно и отказ одного API-процесса (PERF-03, AC-41) — эпоха E5, здесь не проверялись.

### Стенд (задание №3, сборка 4c32ccf, 2026-11-12) и исправление по его итогам
ВМ стенда (4 ядра, 8 ГБ, параллельно работал живой стенд), замер 300 с: 10 736 запросов, 35,8 запроса/с, ошибок 0,
p95 305 мс / p99 545 мс. **SLO не выполнен по чтению:** список p95 402 мс, «Мои задачи» 320 мс (цель ≤ 300); остальное
в пределах (поиск 352, схема 89, правки 404/403, p99 всех 545 мс). Причина: на каждый актив страницы — ~7 запросов
(основные поля, все текущие факты, состояния разделов, три запроса профиля 1.2, ответственный).
Исправление d2d5e12: страница читается одним набором запросов на вид данных; из фактов — только identity/os.
Песочница, тот же сценарий (2 000 активов, замер 120 с), до → после, p95: список 243 → **41 мс**, «Мои задачи»
181 → **23 мс**, карточка 40 → 29, поиск 210 → 165, правки 253 → 225; ошибок 0 (`results/r4-batch.json`).
Повтор на стенде — задание №5 (решение пользователя о выкладке develop).

## 3. Не проверено и ограничения
- На стенде: C27–C30 (оргструктура, сервис поиска как отдельный процесс под systemd, нагрузка на реальном железе).
- Ответственный бизнес-сервиса (ограничение C26); синхронизация оргструктуры — C31.
- Морфология ФИО и прилагательных в поиске (Snowball: «Кузнецова» ≠ «Кузнецов»).
- Hosted CI недоступен до 1.12 (квота): все проверки — локальные повторы шагов CI в песочнице.

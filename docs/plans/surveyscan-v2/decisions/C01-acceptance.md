# C01: приёмка раннего цикла и первого SMB-релиза

Дата: 2026-11-03. Результат C01.04. Scope: [capabilities E1](C01-smb-scope.md).
Этот документ — исполнимый план будущих проверок C08–C14. Статус всех продуктовых
сценариев здесь `unrun`; C01 выполняет только статическую проверку документов.

## 1. Стенд и данные

- Central: Linux/amd64, Go combined, один PG, OpenBao, edge и отдельные Web assets.
- Один постоянный site collector и один настоящий host agent выбранной к C08 ОС;
  процессы и data directories изолированы. Agent OS сейчас предложена, не подтверждена.
- Дополнительный tenant для негативных тестов. Не менее двух разных host identity fixtures;
  настоящий host не подменяется fixture в приёмке C08/C14.
- Исходные ожидаемые hostname/ОС/IP/MAC фиксируются безопасным независимым read-only способом.
  Проверять available/partial, а не требовать недоступные hardware IDs.
- Только синтетические credentials и разрешённые стенды; без реальных данных клиентов.
- Нужен отдельный полноценный host/VM для system-service install и reboot;
  process restart в контейнере не засчитывается как reboot ОС.
- Build versions, commit SHA, стенд, интервалы, продолжительность и номера прогонов фиксируются
  в результате. Не наследовать PASS от документа или старого Python v1.

## 3. Контрольные точки

**C08 — ранний функциональный цикл:** E1-T03 на реальном хосте и относящиеся к нему
проверки схемы/изоляции. Это не означает приёмку очередей, службы, restore или полноценного E1.

**C14 — первый проверяемый SMB:** все применимые E1-T01–15 выполнены в объявленной
матрице, обязательные failures закрыты. Полный AC-44 combined/API-worker production profile
остаётся для C35/C40; E1 проверяет только подготовленные интерфейсы и contract scope.
AC-55 сверяется с capabilities: отложенное не называется реализованным.

Все остальные полные технические AC и E2+/W2/W3 остаются в COVERAGE.md и пакетах плана.
Их отсутствие в минимальном E1 не означает удаление из целевой спецификации.

## 4. План 24-часового прогона E1-T14

1. Создать отдельный run ID, записать commit/versions, конфигурацию интервалов/квот и
   initial counts. Синхронизировать часы стендов; позднее collected_at проверять отдельно от received_at.
2. Подтвердить свежий реальный цикл до начала measured window. Запустить runner,
   который пишет наблюдения/метрики/ошибки и сохраняет status running вне памяти чата.
3. Измерять не менее 24 часов. На выбранных заранее точках разорвать agent→collector,
   collector→center; отдельно перезапустить каждый процесс; проверить получение applied ACK после recovery.
4. Проверить steady-state/recovery memory/CPU/spool, queue/outbox lag, свежесть, section counts,
   постоянство UID и отсутствие повторных эффектов. Бюджеты формируются из измерений;
   C01 не утверждает способность поддерживать 100 пользователей или конкретный расход RAM.
5. Сопоставить ожидаемые и фактически полученные source sequence/observations. Допустимые
   пропуски, например остановленный агент во время reboot, объясняются; подтверждённые результаты не теряются.
6. Завершить run report только после end timestamp и проверки actual duration/results. Если
   окно прервалось, статус interrupted/unrun remaining; не заменять elapsed time коротким mock-run.

Runner не должен блокировать общение долгим sleep. Можно продолжить тот же пакет в следующем
чате по run ID/пути результатов. Ожидание 24 часов не является само по себе прохождением теста.

## 5. Формат доказательства и release gate

Для каждого E1-Txx: run ID, commit SHA, versions, OS/privileges, реальные vs mock targets,
входы, команда/автоматизация, expected, actual, start/end UTC, status, count и artifact paths.
Не включать секреты, дампы private keys или чувствительные клиентские данные.

Нельзя выпускать E1 как принятый при невыполненных обязательных security/durability/service/restore
сценариях. Метки passed/failed/skipped/unrun/running различаются; причина skipped обязательна,
skipped не заменяет обязательную приёмку. Публикация/деплой требуют отдельного фактического результата.

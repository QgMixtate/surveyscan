# C25.01 — сильные/слабые идентификаторы и правила сведения

Статус: R-027. Пользователь выбрал вариант Б (2026-11-10). Реализовано в assets.Store.Resolve; пакет C25 не принят. Основа: спецификация §5, §19 (ID-01…ID-05), C02 §3 (E1: авто-reuse только
своего mapping, совпадение признаков → конфликт). Текущий код: assets.Store.Resolve — любой совпавший кандидат у
нового source record → reconciliation_conflicts, наблюдение recorded_pending_resolution (подтверждено тестом R-027).

## 1. Классы идентификаторов (namespace задаёт нормализацию и область уникальности)
| kind / namespace | Сила | Область | Известные ложные совпадения |
|---|---|---|---|
| machine_uuid / windows-machine-guid | сильный | tenant | клон ВМ/образа без sysprep |
| machine_uuid / linux-machine-id | сильный | tenant | клон ВМ/шаблона с тем же /etc/machine-id |
| bios_uuid / smbios | сильный | tenant | плохие гипервизоры, «FFFFFFFF-…», «03000200-0400-…» |
| serial / smbios, serial / snmp-entity | сильный | tenant | заглушки «0», «None», «To be filled by O.E.M.», «VMware-…» у ВМ |
| snmp_engine_id | сильный (сетевое) | tenant | редкие дубли по умолчанию у вендора |
| cloud_instance_id / <провайдер:аккаунт> | сильный | аккаунт провайдера | — |
| mac / ieee | слабый | scope (L2) | виртуальные/рандомизированные, общие у LAG/VRRP |
| hostname / hostname.raw, dns | слабый | scope | переиспользование имён, переименование |
| ip / scope | слабый | scope (VRF) | DHCP, NAT, перекрывающиеся сети |
IP, MAC и hostname по отдельности никогда не являются ключом (проверка C25.01).

## 2. Недоверенные значения
Сильный идентификатор считается «подозрительным» и для авто-сведения не используется, если: значение в списке
заглушек (по kind); уже есть у ≥2 активов tenant (признак клона); у актива-кандидата есть другой действующий сильный
идентификатор того же kind/namespace (противоречие → конфликт, как сейчас).

## 3. Решение по новому source record (варианты — выбирает пользователь)
А. Только ручное подтверждение (буква C02/C25.02): любое совпадение → кандидаты в очередь разбора; оператор
   подтверждает привязку (аудит, provenance), отказ создаёт отдельный актив.
Б. Авто-привязка по единственному надёжному сильному совпадению: ровно один актив-кандидат в той же tenant/scope,
   совпал ≥1 сильный идентификатор, нет противоречий и подозрительных значений (§2) → запись привязывается к активу
   автоматически с аудитом «AUTO_STRONG_MATCH» и обратима (split C25.03). Всё остальное — в очередь (как А).
   Совпадение только слабых признаков — всегда очередь.
В. Как Б, но включается политикой tenant (по умолчанию выключено).
Во всех вариантах: межtenant связь запрещена; слабые признаки не склеивают; конфликтующие serial/UUID не склеиваются
молча; ручное решение не теряется после следующего наблюдения.

## 4. Проверка (план C25.04)
Фикстуры: физический хост (агент+SSH+WinRM), клон ВМ (тот же machine-id), ВМ с заглушкой serial, сетевое устройство
(SNMP serial+engineID), перекрывающиеся IP в разных scope, межtenant совпадение UUID.

## 5. Решение (R-027)
Выбран вариант Б с уточнением: авто-привязка только между РАЗНЫМИ источниками (агент + SSH + WinRM + portable
одной машины). Две разные записи одного источника с одним сильным ID — признак клона → очередь (сохраняет принятое
поведение C06/C07). Запись, ранее ушедшая в конфликт без актива, авто-привязывается на следующем наблюдении, если
условия выполнены; её открытые конфликты закрываются (state=resolved). Аудит/история/outbox: asset.facts_changed.v1
с reason_code AUTO_STRONG_MATCH (тип события из C03 не менялся). Ручная очередь (C25.02) и split (C25.03) — дальше.

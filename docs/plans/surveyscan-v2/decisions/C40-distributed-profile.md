## C40.03 — нужно ли выделять отдельные сервисы (по замерам, не по числу пользователей)
Замеры (паспорт C30: 2 001 актив, 100 активных пользователей, 300 с): центр — 16–27 % одного ядра и 139–168 МиБ;
сервис поиска (уже отдельный процесс, Rust, C28) — 14 % ядра и 213–252 МиБ; PostgreSQL — ≤ 21 соединения, активных
≤ 5; очередь событий опустошается (максимум 24 события, старейшее 2,4 с); фоновый импорт портативных пакетов 17–19 с
на пакет, не влияя на SLO; p95/p99 91/178 мс в распределённом профиле (r7).
| Кандидат | Решение | Почему | Когда пересмотреть (измеримый порог) |
|---|---|---|---|
| Поиск | **уже отдельный** (C28) | индекс в отдельном процессе, пересборка из PostgreSQL | — |
| Импорт (portable, CSV, наблюдения) | **не выделять** | идёт в роли worker (C35), отдельно масштабируется; узкое место — блокировка записи тенанта (C36.02), выделение её не снимает | очередь импорта > 10 мин в часы пик или p95 API > 300 мс во время импорта |
| Отчёты / схема сети | **не выделять** | пересчёт схемы ~1 с раз в 30 с с кэшем (C36.02); отчёты — чтение | пересчёт > 10 с или > 25 % ядра центра |
| Интеграции (AD, вебхуки, обследования сети) | **не выделять** | фоновые работы под арендой (C35/C36) в worker; внешние сбои изолированы повторами и dead-статусом | > 1 000 доставок/мин или отдельные требования безопасности к сетевому сегменту |
| Маршрутизатор ячеек | **отдельный процесс** (C37) | нужен только при нескольких ячейках | — |
Если порог будет достигнут, порядок выделения такой: владелец (модуль и его схема), отдельный контракт API
(как C51 для машинного канала), догоняющая загрузка из outbox/PostgreSQL, двойная запись не допускается.
Выделение «на вырост» без замера не делается.

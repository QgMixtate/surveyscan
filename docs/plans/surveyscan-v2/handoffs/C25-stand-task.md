# Задание для локального Claude Code: выложить C25 на стенд и проверить слияние/разделение

Исполнитель — Claude Code на ПК пользователя (`C:\work\surveyscan-stand\surveyscan`), доступ к стенду по SSH.
Результат — отчёт пользователю (что сделано, что проверено, цифры, что не получилось). Облачная сессия по отчёту
допишет журнал docs/REQUESTS.md.

## Правила (обязательно)
- Секреты (пароли, токены, ключи, содержимое `.local/vm-center-state`) не выводить в чат и не коммитить.
- sudo на Linux-ВМ — только с паролем, который вводит пользователь; если нужен `/etc/sudoers.d/90-claude-stand` — попросить пользователя.
- Windows DC 10.170.108.1 — только чтение без подтверждения пользователя. В этом задании DC не трогать.
- Агентов (Linux-служба, SSH/WinRM-цели, Windows-служба) не переподключать и не перенастраивать.
- В git с ВМ ничего не пушить. Счётчик плана и статусы пакетов не менять.
- Если шаг не прошёл — остановиться, показать хвост вывода и спросить пользователя; не «чинить» стенд догадками.

## Шаг 1. Код на ВМ (сборка develop, коммит c6e08fb или новее)
У root на ВМ нет доступа к GitHub, код доставляется git bundle:
1. На ПК: `git fetch origin && git checkout develop && git pull`, проверить `git log --oneline -1` (≥ c6e08fb).
2. `git bundle create dev.bundle origin/develop`, скопировать на ВМ (scp в домашний каталог пользователя ВМ).
3. На ВМ от root в `/root/surveyscan`: `git fetch <путь>/dev.bundle refs/remotes/origin/develop:refs/remotes/origin/develop && git checkout -B develop origin/develop`.
4. `cd v2 && make build` — должна завершиться без ошибок.

## Шаг 2. Перезапуск центра (постоянный режим)
Центр работает в root-tmux `center` (`sudo tmux attach -t center`).
1. Перед остановкой записать: число активов, конфликтов, наблюдений (через API или как делали раньше) — «до».
2. Ctrl-C в tmux, затем та же команда: `.contract-tools/bin/python scripts/vm_center.py --persistent --public-host 10.170.108.2 --collector-port 18443`.
3. В выводе должно быть `PERSISTENT стенд найден` и `READY`. Применится одна новая миграция (0038): всего в `platform.schema_migrations` — 39.
4. Через 5–10 минут убедиться, что все 4 источника продолжают доставку (число наблюдений растёт, ошибок нет).

## Шаг 3. Проверка C25.03 на живых данных (обратимый сценарий)
На стенде 2 актива: Linux (записи Linux-агента и SSH-цели surveyscan-ssh1) и Windows (Windows-агент и WinRM2).
Сценарий не меняет UID Linux-актива и в конце возвращает данные:
1. Сохранить «снимок до»: карточка Linux-актива (`GET /api/v1/assets/{uid}`) и его записи
   (`GET /api/v1/assets/{uid}/source-records`): UID, версия, ключи записей, число наблюдений.
2. Разделение: SSH-запись Linux-актива — в новый актив:
   `POST /api/v1/assets/{linux_uid}/split` с `{"source_record_keys":["<ключ SSH-записи>"]}`.
   Ожидаем: `created=true`, новый UID; засечь время ответа.
3. Слияние обратно: `POST /api/v1/assets/merge` с `{"target_asset_uid":"<linux_uid>","absorbed_asset_uid":"<новый UID>"}`; засечь время.
4. Проверить:
   - `GET /api/v1/assets/<новый UID>` → ведёт на Linux-актив (308 или итоговая карточка Linux-актива);
   - у Linux-актива снова обе записи, данные карточки и разделов 1.2 как в «снимке до» (кроме того, что успело прийти новыми наблюдениями);
   - в списке активов снова 2 актива; конфликтов 0;
   - через 10 минут новые наблюдения SSH-цели и Linux-агента применяются к Linux-активу, конфликтов по-прежнему 0.
5. Глазами в Web: карточка Linux-актива → блок «Сопоставление и слияние» показывает 2 записи; скриншот — пользователю.

Запросы к API — сессией администратора: `POST /api/v1/auth/sessions` (имя/пароль — из состояния стенда, не выводить),
дальше cookie сессии и заголовок `X-CSRF-Token` для POST. Можно и через Web UI (кнопки «Выделить в новый актив», «Присоединить карточку к этой»).

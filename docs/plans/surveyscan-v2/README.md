## Результат и границы

50 логических пакетов, 200 подзадач. Один пакет — рекомендуемая тема одного чата,
а не обещание закончить любой объём за один ответ. Число сообщений и токенов заранее не гарантируется.
Большой/заблокированный пакет делится Cxx.a/Cxx.b с сохранением исходных task IDs;
маленькие соседние подзадачи можно закрывать вместе без пересказа всей архитектуры.
Создавать 50 чатов заранее не нужно. C01–C03 завершены как проектирование/контракты; C04 завершён как локальный Go-каркас/dev-стенд; C05 завершён локально; C06 завершён локально; C07 завершён локально; C08 завершён локально; C09 завершён локально; следующий C10.

Принцип: постоянный минимальный agent на хосте → постоянный collector площадки → центр →
постоянная карточка. Portable — разовый аудит; agentless остаётся параллельным сценарием.
Ранний работающий цикл — после C08. E1 является эксплуатационным релизом только после C14:
auth/tenant, identity, outbox, сохранная доставка, отдельный UI, backup и фактическая 24-часовая приёмка.
Демо после C08 не подменяет E1 acceptance. До E2 не заявляется широкий portable/network coverage.

## Как пользоваться планом и экономить контекст

1. Один чат выполняет один выбранный пакет; не отправлять весь план/спеку повторно.
2. В начале прочитать AGENTS.md, актуальный краткий STATUS.md, последние REQUESTS.md,
   [индекс пакетов](TASK_INDEX.md) и только файл выбранного пакета. Затем указанные разделы спеки.
3. Сверить GitHub refs и локальные изменения. Не затирать локальную 0.5 старой опубликованной 0.3.
   Если нового документа нет в checkout, импортировать переданный архив или получить опубликованную ветку.
4. Проверить зависимости: planned не означает done. Нужны коммит/артефакт и фактически выполненные проверки.
5. Не начинать соседние пакеты и не перепроектировать всю систему. Обнаруженный внешний вопрос
   записать как blocker с точной причиной; продолжить независимые подзадачи текущего пакета.
6. В конце сохранить реализацию/документы и запись передачи по [шаблону](HANDOFF_TEMPLATE.md).
   Обновить machine-readable статус и evidence, краткий STATUS и журнал. Никогда не отмечать
   package done по одному плану, сборке без тестов или нулевому числу тестов.
7. Следующему чату передаётся ID пакета + ссылка на артефакт/коммит/ветку. Полная история чата не нужна.
8. Не запускать длинный soak через блокирующее ожидание в чате: runner пишет timestamped results,
   затем тот же пакет продолжается после завершения. До фактического финального результата тест unrun/running.
9. Новые секреты вводятся безопасно через настройки; доступы и реальные targets для пилота должны
   быть явно разрешены. Запрос пакета не означает разрешение на production deployment, push или merge.
10. Любые роли в плане — зоны ответственности. Их может исполнять один человек последовательно;
    план не требует команды из указанного числа специалистов или автоматического запуска субагентов.

## Уровни WBS и правила приёмки

Проект → эпоха/волна → функциональный блок (пакет Cxx) → работа → подзадача Cxx.nn.
В каждом пакете работы сгруппированы на проектирование/подготовку, реализацию и проверку/передачу;
подзадача — конечная единица учёта. У каждой есть роль, вход/зависимость, результат,
критерий проверки и база будущей оценки (объекты, платформы, сценарии).
Часы/стоимость/календарь не назначены: нет утверждённой команды, платформ и производительности.
Это WBS и execution order, не смета и не обязательство по срокам.
Блокирующие решения D-01–18 закрываются к использующему их пакету; полный enterprise ADR не блокирует E1.

## Зависимости и возможные параллельные направления

Обязательный контур E1: C01→C02→C03→C04→C05→C06→C07→C08→C10→C11→C12→C13→C14.
C09 после C06 идёт рядом с C07/C08, но нужен к C12. Это структурная цепочка зависимостей;
реальный календарный критический путь определяется после оценки длительностей/доступности ролей.
После C14 независимы C15/C16 (Windows/Linux), C17/C18 (SSH/WinRM), C19 (netdev).
C20 зависит от remote adapters, C21 — от discovery, C22 — от evidence/presence; C23 portable
может развиваться параллельно после своих базовых зависимостей. C24 сводит весь E2.
C28 PoC поиска может идти рядом с C26/C27 после готовности модели C25.
После C30 бизнес-ветка W2 (C41–45) не обязана ждать физического enterprise/geo C35–40.
ITSM начинается после согласования/приёмки W2. Общая схема эпох — целевой охват, не требование
развернуть несколько регионов прежде чем реализовать склад. Переупорядочение только по зависимостям.
Реальное выделение микросервисов — отдельный измеренно обоснованный scope, C40 лишь принимает решение.

- C01: выбрать первую ОС/архитектуру E1, версии, минимальные поля и допустимость скриптов.
- C11/C13: выбранная версия OpenBao, trust/enrollment и условия защищённого хранения ключей.
- C15–24: реальные разрешённые Windows/Linux/network lab targets и доступы; mock не доказывает совместимость.
- C28: представительный RU/EN корпус и критерии выбора FTS.
- C30: операция/данные/железо/think-time/SLO для 100 активных, а не только зарегистрированных пользователей.
- C31/C32: разрешённые интеграционные доступы, доступные v1 exports/ключи; потерянные данные не восстанавливаются догадкой.
- C34: pilot scope/владельцы/окна/доступы и решение о развёртывании.
- C38/C39: регионы, residency, RPO/RTO, ресурсы DR и способ fencing.
- C41/C46: согласованные бизнес-процессы и роли; детальные AC W2/W3 создаются до кода соответствующей волны.

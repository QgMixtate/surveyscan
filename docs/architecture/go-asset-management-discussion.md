# Go, портативный сбор и Asset Management — обсуждение

Дата: 2026-11-02. Статус: предложение, не утверждённая архитектура. Код не меняется.

## Запрос пользователя (R-004)
1. Компилируемый стек; монолит на Go.
2. Коллектор на Go.
3. Портативная версия (возможен Rust): собирать информацию автономно, затем передавать на сервер.
4. «Целимся в smdb» — требуется уточнить, имеется ли в виду CMDB.
5. PostgreSQL с расчётом на шардинг.
6. PgBalancer — уточнить конкретный продукт либо требование к пулу/балансировке.
7. Продукт должен входить в Asset Management.
Сначала обсудить, миграцию пока не начинать.

## Предложение
Модульный сервер-монолит Go: API, авторизация/RBAC, реестр активов, нормализация, идентификация,
история наблюдений, отношения, задания и импорт в одном приложении. PostgreSQL отдельно.
Сборщик — отдельный Go-бинарник с общим SDK/моделью наблюдений, режимами service, portable и local.
Портативная версия также на Go; Rust вводить только при подтверждённой необходимости.
UI — предварительно собранные локальные веб-ресурсы, встроенные в сервер/portable через go:embed.
Это не означает компиляцию браузерного JavaScript в машинный код; требование уточнить.

## Сбор и зависимости
Remote-режим: SSH/WinRM/SNMP и при необходимости специализированные API.
Local-режим: запускаемый на целевом Windows/Linux узле бинарник, нативные API ОС.
Портативный сетевой сбор с ноутбука требует доступных протоколов и прав на удалённых узлах.
Go-сборщик, выполняющий PowerShell/sh, всё ещё зависит от интерпретатора на цели.
Для строгого запрета скриптов нужны нативные адаптеры и отдельная проверка покрытия.
Nmap — явная внешняя зависимость при сохранении; заменить его эквивалентом на Go не является
малой задачей. Решить, допустим ли он как дополнительный сканирующий движок.
Отдельные сборки под ОС/архитектуры; минимальные поддерживаемые Windows/Linux версии проверять.

## Автономная передача
Предварительно предложенный формат .survpack:
- manifest: версия схемы, UUID пакета, организация/площадка, scope скана, версии сборщика,
  начало/конец сбора, перечень файлов, размеры и контрольные суммы;
- поток наблюдений (например, NDJSON), ошибки/статусы секций и разрешённые исходные артефакты;
- подпись источника с проверкой доверия; шифрование на публичный ключ получателя;
- секреты подключения не входят в пакет; источник и время сбора отличать от времени импорта.

Online: HTTPS с аутентификацией, возобновление передачи и подтверждение приёма.
Offline: перенос файла, импорт через серверный UI/API.
Оба пути используют одинаковую валидацию/нормализацию и дедупликацию package_id.
Сервер проверяет принадлежность пакета организации по авторизации, не доверяет tenant_id из файла.
Ограничения распаковки, числа записей и размера; обработка несовместимой версии схемы.
Поздняя выгрузка сохраняет историю, но не перезаписывает более свежие данные без правил согласования.
Подпись подтверждает источник/целостность, а не достоверность сведений самого хоста.
Предпросмотр локально можно делать через UI на loopback с временным токеном и локальным журналом.
SQLite возможен для рабочего состояния портативной версии; серверный формат обмена — пакет, не дамп БД.

## Модель Asset Management / возможная CMDB
Долгоживущий asset UUID, идентификаторы источников, tenant/site, тип, жизненный цикл, владелец,
ответственный, назначение, критичность и связи. Отдельно: сканы, наблюдения, история и текущая проекция.
Идентификация по нескольким признакам (серийный номер, UUID VM, ID провайдера, домен и т.д.);
IP/MAC/hostname по отдельности недостаточны. Ручные бизнес-поля сбором не затирать.
Хранить источник и свежесть каждого поля; не трактовать один неудачный скан как списание актива.
Если CMDB подтверждена: CI, типизированные отношения и зависимости сервисов.
Финансовый/лицензионный учёт — отдельное согласование объёма Asset Management.

## PostgreSQL и масштабирование
Начало: один кластер, нормальные таблицы вместо БД на скан, индексы и измерения нагрузки.
JSONB для вариативных фактов; ключевые сущности и связи реляционные.
Историю партиционировать по времени по необходимости. Партиционирование не равно шардингу.
Кандидат ключа шарда: tenant_id для независимых организаций; site_id требует оценки межплощадочных связей.
Не делать обязательных межшардовых транзакций; глобальные отчёты и крупного tenant проектировать отдельно.
UUID, scoping запросов, составные ограничения с tenant_id, проверка изоляции; routing отделить от доменной логики.
Шарды/реплики/пул соединений/аварийное переключение — разные механизмы.
PgBouncer — пул; pgBalancer — отдельный продукт. Выбор не утверждён.
Балансировщик не выбирает бизнес-шард автоматически. Для чтения с реплик учитывать задержку репликации.

## Следующий этап обсуждения
Уточнить CMDB, конкретный pgBalancer/PgBouncer, тип portable, масштабы и запрет скриптов.
Затем согласовать схему данных/контракт пакета и вертикальный срез:
Go portable → один Windows/Linux хост → пакет → Go server → постоянная карточка → повторный импорт без дублей.
Переносить Python-функции постепенно, сохранив фикстуры и проверку эквивалентности.
Не считать предыдущие ветки автоматически слитыми или отменёнными.

# Руководство оператора SurveyScan v2 (C33.03)

Сводка процедур по ситуациям. Подробные проверенные процедуры — в [RELEASE.md](RELEASE.md), [UPDATE.md](UPDATE.md),
[BACKUP.md](BACKUP.md), [systemd/README.md](systemd/README.md). Поддерживаемые платформы — только из
[таблицы поддержки](../../docs/plans/surveyscan-v2/decisions/C33-support-matrix.md). Секреты (пароли, токены,
ключи, grant) в этот документ, тикеты и чаты не копируются — только пути к приватным файлам (права 0600).

Отметки: **[проверено]** — прогон на стенде или ВМ с протоколом; **[CI]** — автоматическая проверка;
**[не проверено]** — процедура описана, независимый прогон (C33.04) ещё не сделан.

## 1. Установка центра [проверено: 2 свежие ВМ Debian 12/systemd 252 (C13); стенд Ubuntu 24.04 — через vm_center]
1. Предпосылки: PostgreSQL 17, OpenBao 2.7.2, TLS-сертификаты edge, systemd ≥ 252, Linux amd64.
2. Проверить подпись выпуска: `release.py verify --bundle B --public-key PUB`; установить: `release.py stage`.
3. Учётные записи (sysusers), приватные конфиги 0600 в `/etc/surveyscan-server`, `LoadCredential` — по
   [systemd/README.md](systemd/README.md). Миграции — служба `surveyscan-migrate` (до сервера).
4. Первый администратор: `surveyscan-server bootstrap-admin --tenant … --password-file …` (пароль — из файла,
   не в аргументах). Площадка и резервная команда — заводятся до регистрации источников.
5. Необязательно: сервис поиска (`bin/surveyscan-search 127.0.0.1:PORT DATA TOKEN_FILE`, `search_url`/`search_token_file`
   в machine.json).
6. Хранилище секретов интеграций (один раз при установке): в политике OpenBao центра — правило
   `path "<kv>/data/server/integrations/*" { capabilities = ["create","update","read"] }`, в bao.json —
   `"integrations_path": "server/integrations"` (обвязка стенда `vm_center.py` добавляет их сама). После этого AD и
   уведомления включаются **из Web** без правки конфигурации (разделы 8, 9).
Проверка: `healthcheck`, вход в Web, `GET /api/v1/diagnostics` без предупреждений.

## 1а. Несколько экземпляров (C35) [CI: split_smoke]
Один процесс по умолчанию (`combined`). Для разделения: `SURVEYSCAN_V2_ROLE=api` — UI/API и транспорт агентов
(можно несколько за балансировщиком, у каждого свой `SURVEYSCAN_V2_LISTEN` и `listen` в machine.json);
`SURVEYSCAN_V2_ROLE=worker` — фоновая работа (можно 2 для отказоустойчивости), отвечает только на `/health/*`.
Все процессы — одна БД, один OpenBao, один сервис поиска. Сессии и задачи не теряются при остановке одного api.
**Каждому api — своя копия machine.json** (отличается только `listen`): в ней же адрес сервиса поиска и включение
протокола 1.2. api без machine.json работает, но ищет перебором по PostgreSQL — под нагрузкой это таймауты (C40.01).
За маршрутизатором ячеек (C37) несколько api одной ячейки задаются `backends` — запросы раздаются по кругу.

## 2. Обновление [проверено: C13 — проверенное обновление с откатом при неудачном старте, SIGKILL updater]
`updater.py prepare --bundle B --revocations R` → `updater.py apply --health-url …` → при сбое — автоматический
откат на прежний выпуск; незавершённое — `updater.py recover`. Схема БД только дописывается: откат после
применённой миграции — **только восстановлением из резервной копии** (раздел 3), не сменой ссылки на выпуск.
Порядок для всего контура и условия остановки — [RELEASE.md, C33.02](RELEASE.md). Отозванный выпуск не ставится.
**Web обновляется отдельно от центра** (независимая версия, C14/C40): после обновления центра пересобрать и выложить
статический Web (`npm ci && npm run generate && npm run build` → каталог показа Web) и проверить `version.json` —
иначе новые разделы и поля не появятся, а несовместимую пару Web↔API Web сам покажет как ошибку версии.

## 3. Резервная копия и восстановление [проверено: C13 — PostgreSQL, OpenBao Raft, общий checkpoint с повтором]
Ежедневно: дамп PostgreSQL + снимок OpenBao Raft + файлы состояния центра — по [BACKUP.md](BACKUP.md); хранить
отдельно от сервера; ключи OpenBao (unseal) — отдельно от копий. Восстановление — на чистую БД, затем запуск
центра (миграции догоняют), проверка входа и записи. Индекс поиска в копию не входит: пустой индекс центр
пересобирает сам (`search index rebuilt` в журнале).

## 4. Источник перестал присылать данные
1. Web «Источники»: «последний контакт» есть, «успешный сбор» старый → сбор падает на хосте (журнал агента:
   `journalctl -u surveyscan-agent` / Журнал событий Windows, служба SurveyScan Agent).
2. Контакта нет → сеть/сертификат: с хоста `surveyscan-agent renew --config …` (обновление сертификата) [CI]; при
   отказе «unknown source» — источник отозван/удалён в центре: повторная регистрация новым grant.
3. Агент копит данные в очереди на диске и досылает после восстановления связи [проверено: C10/C15 — reconnect,
   SIGKILL, офлайн-очередь]. Переподключать (enroll заново) **не нужно** — иначе появится новый источник.

## 5. Диск заполнен [CI: реальный ENOSPC в tmpfs]
- Агент/collector: очередь ограничена `spool_limit_bytes` профиля источника и 7 сутками; при нехватке места новые
  пакеты не пишутся, служба не падает; освободить место — сбор и досылка продолжаются сами.
- Центр/PostgreSQL: остановить импорт portable-пакетов, освободить место (старые копии, журналы), проверить
  `healthcheck`. Не удалять файлы в каталогах данных PostgreSQL/OpenBao вручную.

## 6. Центр не стартует [частично проверено: откат при неудачном старте — C13]
`journalctl -u surveyscan-migrate -u surveyscan-server`: «drift»/миграция — не править схему вручную, раздел 2/3;
OpenBao sealed — распечатать по процедуре организации; «private configuration file» — права файла не 0600 или
неверный путь `LoadCredential`; `ldap_sync`/`webhook_secret_file` с ошибкой — центр не стартует намеренно
(исправить конфиг или убрать блок).

## 7. Поиск недоступен [CI: интеграционный тест C29; стенд — задание №3]
Плашка в Web — поиск работает в точном режиме по PostgreSQL. Проверить процесс `surveyscan-search`, токен-файл,
`search_url`. После перезапуска центр догоняет изменения; при смене формата — пересобирает индекс сам
(`POST /api/v1/search/rebuild` — вручную, администратор).

## 8. Синхронизация с AD [CI и демо: мок OpenLDAP по LDAPS через OpenBao; реальный AD — **не проверено**]
Включение: «Оргструктура» → «Настроить подключение к AD» → адрес `ldaps://…`, base DN, DN учётки только на чтение,
пароль (сохраняется в OpenBao, обратно не показывается), сертификат CA (PEM), при необходимости фильтр групп →
«Проверить подключение» (ничего не меняет) → «Сохранить». Блок `ldap_sync` в machine.json по-прежнему работает и
имеет приоритет (настройки в Web тогда только для просмотра). «Отключить» — люди из каталога остаются, не обновляются.
Сбои — панель синхронизации. `failed`: «bind failed» — учётка/пароль (файл `bind_password_file`);
«directory unavailable … certificate» — CA (`ca_certificate_file`); «would deactivate too many» — полный снимок
убрал бы > ¼ людей: проверить фильтры, ничего не применено. Учётка AD — только чтение.

## 9. Уведомления [CI: тестовый HTTPS-получатель; демо: включение кнопкой через OpenBao]
Включение: «Уведомления» → «Включить уведомления» (центр создаёт мастер-ключ в OpenBao; его не видно и не нужно
копировать). Подписка: адрес https получателя и события → секрет подписи показывается **один раз**.
Не доставляются:
«Уведомления» → «Доставки»: ответ получателя и следующая попытка. После 5 неудач — «не доставлено»; после
устранения причины — «Повторить» (попадает в аудит). Смена секрета подписи — новая подписка.

## 10. Ротация сертификатов и ключей [CI: TLS-ротация агента и collector с потерей подтверждения]
Агент/collector: обновление сертификата — `renew` (выполняется и автоматически до истечения); после ротации CA
центра — по [systemd/README.md](systemd/README.md) (пины CA проверяет оператор). Ключ подписи выпусков — у
ответственного за выпуск, вне серверов; при компрометации — новый ключ, новый выпуск, старые версии — в список отзыва.

## 11. Подготовка ПК Windows к сбору по WinRM через GPO [на стенде — не проверено]
Скрипт `deploy/windows/prepare-winrm-target.ps1` нужен для одного-двух ПК. Для домена ПК готовятся групповой
политикой: один раз в GPO — дальше все ПК в OU готовы сами (новые — после входа в домен и перезагрузки).
Права учётки сбора — только чтение: она **не** администратор ПК.

**Что нужно заранее.** Доменная группа, например `SurveyScan-Collect`, в ней учётка сбора (`AWM\scanwinrm`);
адрес collector (например `10.170.108.2`); OU с ПК; общая папка, доступная на чтение «Компьютерам домена»
(обычно `\\awm.local\NETLOGON\surveyscan\`), с файлом `prepare-winrm-target.ps1`.

**GPO «SurveyScan WinRM»** (Конфигурация компьютера), привязать к OU с ПК:
1. *Настройка → Параметры панели управления → Локальные пользователи и группы* (Preferences → Local Users and
   Groups): действие «Обновить» для встроенных групп **«Пользователи удалённого управления (встроенная)»**
   (Remote Management Users, S-1-5-32-580) и **«Пользователи DCOM (встроенная)»** (Distributed COM Users,
   S-1-5-32-562): добавить `AWM\SurveyScan-Collect`. Группы выбираются из списка встроенных — работает на ПК с
   любым языком Windows.
2. *Политики → Конфигурация Windows → Параметры безопасности → Системные службы*: «Служба удалённого управления
   Windows (WS-Management)» — **Автоматически**.
3. *Политики → Административные шаблоны → Компоненты Windows → Удалённое управление Windows (WinRM) → Служба
   WinRM*:
   - «Разрешить удалённое управление сервером через WinRM» — **Включено**, фильтр IPv4 — адрес collector
     (не `*`);
   - «Разрешить проверку подлинности Basic» — **Отключено**; «Разрешить незашифрованный трафик» — **Отключено**;
   - «Запретить проверку подлинности Kerberos» — **Отключено** (Kerberos нужен для сбора по HTTP 5985);
   - «Запретить WinRM хранить учётные данные RunAs» — **Включено**.
4. *Политики → Конфигурация Windows → Параметры безопасности → Брандмауэр Защитника Windows в режиме повышенной
   безопасности → Правила для входящих подключений*: TCP **5985** (Kerberos по HTTP) и/или **5986** (HTTPS),
   удалённый адрес — только адрес collector, профиль «Домен».
5. Права на чтение WMI (`root\cimv2`: «Включить учётную запись» + «Удалённое включение») групповой политикой не
   задаются — их выдаёт скрипт: *Настройка → Параметры панели управления → Назначенные задания → Немедленная
   задача (Windows 7 и выше)*, от имени `NT AUTHORITY\SYSTEM`, «Выполнять с наивысшими правами»:
   `powershell.exe -NoProfile -ExecutionPolicy Bypass -File \\awm.local\NETLOGON\surveyscan\prepare-winrm-target.ps1 -Account AWM\SurveyScan-Collect -Collector 10.170.108.2 -Gpo`
   Ключ `-Gpo`: скрипт только выдаёт права WMI (группы, служба, прослушиватель и брандмауэр — из GPO) и
   создаёт HTTPS-прослушиватель, если на ПК есть сертификат от CA домена (автоподача, п. 6). Скрипт идемпотентен:
   повторный запуск ничего не ломает.
6. Для HTTPS с «CA домена» (без ручных PEM): *Политики → Конфигурация Windows → Параметры безопасности → Политики
   открытого ключа → Клиент служб сертификации — автоматическая регистрация* — **Включено** (обновлять и
   продлевать сертификаты); в AD CS — шаблон «Компьютер» (или его копия с проверкой подлинности сервера) с правом
   «Автоматическая регистрация» для «Компьютеров домена».

**Проверка на ПК** (после `gpupdate /force` и перезагрузки): `winrm enumerate winrm/config/listener` — есть
прослушиватель на 5985 (и 5986, если есть сертификат домена); `net localgroup` встроенных групп — есть группа сбора.

**В SurveyScan.** (Kerberos по HTTP и «CA домена» — в работе, C51.03 шаги 2–3; сейчас доступен HTTPS 5986 с
сертификатом, запомненным при первом подключении, или с PEM.) Цель создаётся в «Обследования сети» → «Собирать…» у найденного узла:
- **HTTP 5985 + Kerberos** — имя ПК (FQDN, например `win-ar.awm.local`) и доменная учётка; NTLM по HTTP не
  используется — без Kerberos сбор не начнётся; сообщения шифруются Kerberos;
- **HTTPS 5986** — проверка сертификата: «CA домена» (корневой сертификат AD CS загружается один раз на вкладке
  «Учётки сбора»), «запомнить при первом подключении» или PEM конкретного ПК.

## Что ещё не проверено независимо (C33.04)
Установка «с нуля» по этому документу оператором, не писавшим его; восстановление на стенде пользователя;
реальный AD; Windows 10/11; дистрибутивы кроме Debian 12/Ubuntu 24.04.
